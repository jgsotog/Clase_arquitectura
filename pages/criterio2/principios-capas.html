Tema 2.5

Principios de la Arquitectura en Capas

Los principios arquitectonicos son las reglas fundamentales que guian el diseno de sistemas de software de calidad. Comprender estos principios permite tomar decisiones informadas sobre la organizacion y estructura del sistema.

Principio 1: Acoplamiento

El acoplamiento mide el grado de dependencia entre modulos o componentes de un sistema. Un acoplamiento bajo (loose coupling) es deseable porque permite modificar un componente sin afectar a los demas. Un acoplamiento alto (tight coupling) dificulta el mantenimiento y la evolucion del sistema.

Problema: Alto Acoplamiento

Cuando un modulo depende fuertemente de los detalles internos de otro, cualquier cambio en uno requiere cambios en el otro.

Solucion: Bajo Acoplamiento

Cada capa expone una interfaz publica limpia. Los detalles internos estan ocultos. Los cambios internos no afectan a otras capas.

Nivel Tipo Descripcion Calidad
1 Acoplamiento de datos Los modulos comparten datos a traves de parametros simples Mejor
2 Acoplamiento de marca Los modulos comparten una estructura de datos compuesta Bueno
3 Acoplamiento de control Un modulo controla el flujo de otro mediante banderas Regular
4 Acoplamiento externo Los modulos comparten un formato de datos externo impuesto Regular
5 Acoplamiento comun Los modulos comparten datos globales Malo
6 Acoplamiento de contenido Un modulo modifica el contenido interno de otro Peor

Principio 2: Cohesion

La cohesion mide cuanto se relacionan las responsabilidades dentro de un mismo modulo. Una alta cohesion es deseable: significa que el modulo tiene un proposito claro y todas sus funciones contribuyen a ese proposito. Una baja cohesion indica que el modulo hace demasiadas cosas no relacionadas.

Nivel Tipo de Cohesion Descripcion Calidad
7 Funcional Todas las partes contribuyen a una sola tarea bien definida Mejor
6 Secuencial Las salidas de una parte son entradas de la siguiente Buena
5 Comunicacional Las partes operan sobre los mismos datos Buena
4 Procedimental Las partes deben ejecutarse en un orden especifico Regular
3 Temporal Las partes se ejecutan al mismo tiempo pero no se relacionan Regular
2 Logica Las partes estan relacionadas logicamente pero hacen cosas distintas Mala
1 Coincidental Las partes no tienen ninguna relacion entre si Peor

Principio 3: Niveles de Abstraccion

Cada capa en una arquitectura en capas representa un nivel de abstraccion diferente. Las capas superiores son mas abstractas (cercanas al usuario) y las inferiores son mas concretas (cercanas al hardware o almacenamiento).

Capa mas alta = Mayor abstraccion

La capa de presentacion usa conceptos como "mostrar producto" o "formulario de registro". No necesita saber si los datos estan en MySQL o MongoDB.

Capa media = Abstraccion intermedia

La capa de negocio usa conceptos como "calcular descuento" o "validar pedido". No necesita saber como se muestra en pantalla ni como se guarda en disco.

Capa mas baja = Menor abstraccion

La capa de datos usa conceptos como "INSERT INTO productos" o "db.collection.find()". Trabaja con los detalles concretos del almacenamiento.

Principio 4: Separacion de Responsabilidades (SoC)

El principio de Separacion de Responsabilidades (Separation of Concerns) establece que cada modulo debe ocuparse de una sola preocupacion o aspecto del sistema. Este es el principio que fundamenta toda la arquitectura en capas.

Resumen de Principios

Principio Objetivo Metrica
Bajo Acoplamiento Minimizar dependencias entre modulos Menos conexiones entre componentes = mejor
Alta Cohesion Maximizar la relacion interna de un modulo Funciones mas relacionadas dentro del modulo = mejor
Abstraccion Ocultar detalles innecesarios Menos detalles expuestos entre capas = mejor
Separacion de Responsabilidades Una responsabilidad por modulo Menos razones para cambiar un modulo = mejor
Ocultamiento de Informacion Proteger detalles de implementacion Interfaces publicas minimas y estables = mejor
