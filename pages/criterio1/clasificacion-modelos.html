Tema 1.3

Clasificacion de Modelos Arquitectonicos

Los modelos arquitectonicos se organizan en taxonomias que permiten entender sus diferencias, similitudes y contextos de uso. Conocer esta clasificacion es esencial para elegir el modelo correcto para cada problema.

Taxonomia de Modelos Arquitectonicos

Segun Garlan y Shaw (1994), los modelos arquitectonicos se pueden clasificar en las siguientes categorias principales. Cada una agrupa estilos con caracteristicas comunes.

Se enfocan en como se organizan los componentes del sistema y las relaciones estaticas entre ellos.


Modelo Descripcion Ejemplo
En Capas Organiza el sistema en capas jerarquicas, cada una ofrece servicios a la capa superior Modelo OSI, aplicaciones web MVC
Orientado a Objetos Componentes son objetos que encapsulan datos y comportamiento Sistemas empresariales Java, aplicaciones .NET
Basado en Componentes Componentes reutilizables e intercambiables con interfaces bien definidas Plugins de Eclipse, componentes React

Se centran en como los datos fluyen a traves del sistema, siendo transformados por cada componente.


Modelo Descripcion Ejemplo
Pipe and Filter Datos fluyen por tuberias entre filtros que los transforman Unix pipes, compiladores, ETL
Batch Sequential Procesos por lotes que se ejecutan en secuencia Procesamiento nocturno de bancos

Los componentes interactuan a traves de un almacen de datos central al que todos tienen acceso.


Modelo Descripcion Ejemplo
Repositorio Almacen central pasivo, los clientes consultan y modifican Bases de datos, sistemas de archivos
Pizarron (Blackboard) Almacen activo que coordina agentes especializados Reconocimiento de voz, IA diagnostica

La interaccion se basa en invocaciones de funciones, metodos o servicios que retornan resultados.


Modelo Descripcion Ejemplo
Programa Principal / Subrutina Control jerarquico top-down Programas en C clasico
Cliente-Servidor Clientes solicitan servicios a servidores Aplicaciones web, APIs REST
RPC / Microservicios Llamadas remotas entre servicios distribuidos gRPC, arquitecturas de Netflix

Los componentes se comunican mediante la emision y recepcion de eventos, sin conocerse directamente entre si.


Modelo Descripcion Ejemplo
Publish-Subscribe Publicadores emiten eventos, suscriptores los reciben Kafka, RabbitMQ
Event-Driven El flujo del sistema esta guiado por eventos Interfaces graficas, IoT
Event Sourcing El estado se reconstruye a partir de la secuencia de eventos Sistemas financieros, auditoria

Criterios para Seleccionar un Modelo

Naturaleza del Problema

Problemas de transformacion de datos sugieren Pipe & Filter. Problemas con multiples fuentes de conocimiento sugieren Blackboard. Problemas de negocio empresarial sugieren Capas o Microservicios.

Requisitos de Calidad

Si el rendimiento es critico: minimizar capas. Si la escalabilidad es clave: considerar microservicios. Si la mantenibilidad importa: modelos con alta cohesion y bajo acoplamiento.

Tamano del Equipo

Equipos pequenos se benefician de monolitos bien estructurados. Equipos grandes necesitan arquitecturas que permitan trabajo independiente (microservicios, componentes autonomos).

Restricciones Tecnologicas

Sistemas embebidos requieren modelos ligeros. Aplicaciones web tipicamente usan cliente-servidor o capas. Sistemas distribuidos a gran escala requieren Event-Driven o Microservicios.
